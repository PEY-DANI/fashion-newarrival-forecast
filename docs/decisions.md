## D3. 수집 범위 — 일부 결정 (2026-10-07)

| 항목 | 결정 | 이유 |
|---|---|---|
| 카테고리 | **우선 반소매 티셔츠 1종만** (이후 다른 카테고리도 수집 예정) | 패션은 변수가 많아서 범위를 좁힌다. 한 카테고리로 먼저 해본다 |
| 성별 | **여성 + 공용** — 목록 API `gf=F` 조회 결과를 그대로 사용하고 `displayGenderText`로는 거르지 않는다 (빈값도 포함) | 여성을 대상으로 하되 공용도 포함하는 게 맞다고 판단. `gf=F` 결과에 남성으로 표시된 상품이 있었으나 상품 페이지에서는 모두 공용으로 표기되어 있어서, `gf=F` 결과를 여성 대상 상품 전체로 본다 |
| 예측 목적 | **2026년 여름(6~8월)** 등록 상품 예측 | |
| 등록일 범위 | **2024-05-01 ~ 2026-08-31**. 2024·2025·2026년 여름 3시즌이 포함된다 | 시즌 전에 미리 등록되는 상품이 있을 수 있어서 시작을 5월로 당김 |
| 등록 월 | **전부 사용** (여름 외 달 포함) | |
| 16주 관측 부족분 | **지금 수집하고, 나중에 부족한 부분만 다시 받는다.** 2026년 여름 상품은 16주 창이 2026-12-21경 완성된다 | |

| 카테고리별 브랜드 효과 | 수집 전에 미리 확인하지 않는다 | 그 차이 자체가 분석 결과로 쓸 수 있는 부분이기 때문 |

아직 정하지 않은 것:

- [ ] 위 결정의 세부: 목록을 끝까지 훑을 때의 '조건', 품번이 가리키는 필드(`style_no` / `goods_no`)
- [ ] 리뷰 구간 수 (4구간 유지 / 줄이기)
- [ ] 사진 조건 (수집 때 거르기 / 분석 때 처리)

## D3-1. 목록 수집 방식 (2026-10-08)

| 항목 | 결정 | 이유 |
|---|---|---|
| 조회 조건 | 목록 API `gf=F`, `isComingSoon=false`(판매예정 제외), `category=001001` | |
| 수집 필드 | **목록 API에서 받을 수 있는 값만** 받는다 | 상품 API와 비교해 같은 의미의 값이 모두 일치했고, 상품 API에만 있는 값은 라벨·플러스배송뿐 |
| 등록일 필터 | 썸네일 URL에서 추출한 등록일이 범위(2024-05-01 ~ 2026-08-31) 밖이면 **수집에서 제외** | |
| 페이지 크기 | **`size=100`** | 목록 API 최대값 (`size=101`부터 400 오류). 여성 반소매 기준 약 766페이지 |
| 요청 간격 | **2초** | |
| 중복 | **상세 단계 이후**(상세·`/stat`·리뷰·이미지)에서 기존 수집분에 있는 상품(`goodsNo` 기준)은 **다시 받지 않고** 기존 정보를 쓴다. 목록 단계는 전부 새로 받는다. 기존 수집분의 기준은 **서버**(로컬보다 최신) | 대상은 전체 목록이고, 이미 받은 상품의 중복 수집만 피한다. 목록 API는 페이지 단위라 중복을 걸러도 요청이 줄지 않는다 |
| 수집 날짜 | 모든 수집 값에 **수집 날짜를 함께 기록**한다 | 가격·리뷰 수 같은 값은 수집 시점마다 달라지므로 날짜로 구분해 관리한다 |
